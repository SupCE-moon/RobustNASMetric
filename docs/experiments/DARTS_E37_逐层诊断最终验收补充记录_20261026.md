1. v2 的“分量→保存分数”和“保存分数→strict”两段容差可串联放大误差。现要求分量重建值**直接**与 strict 参考比较，仍用原固定容差 `3e-8 + 3e-5 × |strict|`。构造 Fisher 为 strict `0.3`、保存值 `0.300007`、分量重建值 `0.300014` 的回归现为 FAIL。
2. `diagnostic`、锚层或样本为 `null`，以及异常巨大的 feature_count、分量整数，曾可能让核验过程异常退出而不写失败证据。现先检查嵌套对象及 feature_count 范围，并将过大数值判为非有限；对应回归均返回 FAIL 和精确修复键。
3. 原始记录自称 `status=ok` 但未通过数值/结构核验时，既不能算有效成功，也不能删除。现将其列为 `rejected_attempts`，保留原文件；正式文件级核验另记相对路径和 SHA-256。只有来源、冻结 manifest、检查点、代码与协议均一致，且同键后来恰好一个完整有效成功，才允许最终 PASS；两种扫描顺序均有回归测试。来源错误、未知键、重复有效成功及跨阶段锚层身份不符仍是致命错误，不会被补跑抵消。运行器的修复模式复用完整核验器分类，只接受与核验出的全部缺失/拒绝键**完全相同**的 CSV，不能仅凭原始 `status=ok` 判定。

上述机制是未来失败时的安全补跑规则，不表示本次正式采集曾出现失败。首次服务器测试误指定了不存在的测试文件（0 tests）、v1/v2 的问题复现，以及 v3 后发现的极端整数溢出，都保留为过程问题；没有伪造或删除失败记录。已分别保存服务器程序的 `.pre_v3`、`.pre_v3b` 副本，v1/v2/v3 验收目录未覆盖。
