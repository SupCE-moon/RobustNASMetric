## D-001 Git 准入策略：按路径与大小判定，10 MiB 警告 / 50 MiB 拒绝

**背景**：项目里有 45 个 RobustBench 权重文件、CIFAR-10 数据、checkpoint、逐样本原始行，
以及生成表格时产生的 `node_modules`。历史上没有统一规则，靠人工记得"别提交大文件"。

**选择**：`tools/repository_policy.py` 用一条确定性规则判定每个文件是否可入库：
禁用后缀（权重/数组/压缩包/PDF/密钥）、禁用目录（`.venv`、`checkpoints`、`secrets`）、
文件名含 `secret`/`credential`/`password` 等直接拒绝；≥10 MiB 警告，>50 MiB 拒绝。

**理由**：规则必须能被测试和 CI 复用，而不是写在文档里靠自觉。用"路径 + 大小"而不是内容，
是因为判定时不需要读文件，几万个文件也能秒级完成。

**后果**：两个 13.94 MiB 的合并原始值表被判定为"警告"，导入工具据此暂缓（见 D-003）。

## D-002 结果表用"显式清单 + 强制添加"，而不是改宽 `.gitignore`

**背景**：`.gitignore` 只忽略了 `outputs/` 下的少数子目录，大部分 CSV 本来就可入库；
但有些目录（`pytest_temp_full/`、`node_modules/`）必须排除。

**选择**：保持 `.gitignore` 的保守默认（新增 `node_modules/`、`~$*`），
导入时以 `import-plan-main.json` 这份**逐文件清单**为准，清单里 `action=import` 的文件才复制。

**理由**：`.gitignore` 只能按模式排除，无法表达"这个 CSV 要、那个 CSV 不要"。
显式清单同时满足对账规范里的"显式清单"要求，并且每个文件都带 SHA-256，事后可核。

**后果**：将来新增结果文件不会被自动跟踪，需要重新生成清单——这是刻意的：
入库应当是有意识的动作。

## D-004 在 worktree 里跑测试必须显式设置 `PYTHONPATH`

**背景**：共享 `.venv` 以 editable 方式安装了 `robust_metric_lab`，指向主工作树。
在 `.worktrees/mainline-consolidation` 里直接 `pytest` 时，导入的其实是主工作树的源码——
第一次运行就出现了"测试读的是另一个目录的 metrics.py"的诡异报错。

**选择**：所有 worktree 内的测试命令都前置
`$env:PYTHONPATH="<worktree>\src"`，并在提交信息里记录这一点。

**理由**：否则测试结果与被测代码不是同一份，"57 passed"没有意义。重装 editable 包会污染
主工作树的环境，不可取。

**后果**：这是本项目最容易踩的坑之一，后续任何人（包括我）在 worktree 里验证都必须照做。

## D-005 服务器盘点用只读 SSH 普查，密码不落地

**背景**：服务器 `/workspace/robust_metric_lab_nas` 不是 Git 工作区，且本机没有
`sshpass`/`plink`/私钥，只有 OpenSSH 客户端（密码交互式读取 tty，脚本无法喂入）。

**选择**：`tools/server_inventory.py` 用 paramiko 连接，把一段内嵌 Python 程序通过
`python3 -`（或 `docker exec -i <容器> python3 -`）送到服务器执行；程序只做 `os.walk` +
`stat` + `sha256`，输出 JSON 到本地。密码只从环境变量或 `getpass` 读取，
不接受命令行参数、不写文件；主机密钥未知时直接拒绝连接。

**理由**：满足"服务器只读"和"密码不入 Git"两条硬约束；同时把哈希计算放在服务器侧，
避免把 200+ GiB 数据拉回本地。

**后果**：大文件默认只记录大小/时间（`--hash-limit-mb`，默认 64 MiB），
需要完整哈希时用 `--hash-limit-mb -1` 单独跑一次。

## D-007 为一批导入模块应用了 4 行注册声明（有条件的例外）

**背景**：从 `codex/adv-excess-metric` 导入的 `student_runner.py`、`student_benchmark.py` 等
4 个模块，按名字调用 `feature_adv_excess_centered_unit_l2`；这个名字只存在于该 worktree
**未提交**的 `metric_registry.py` 中。不补这 4 行，导入的模块一调用就 `KeyError`，2 个测试变红。

**选择**：把该改动单独保存为 `patches/adv-excess-uncommitted-metric-registry.patch` 并**应用**
（只加一条 `MetricSpec("feature_adv_excess_centered_unit_l2", "lower", "Ours preregistered
adversarial-excess feature drift", "Ours")`）。

**理由**：这与 D-003 的情况不同。D-003 那 571 行是**未评审的指标数学实现**，风险在"算法对不对"；

**后果**：`pytest tests -q` 从 101 passed / 2 failed 变为 **103 passed**。
若将来判定该指标不应入榜，删掉这条声明即可，不影响其他代码。

## D-008 认定 `codex/server-mainline`（dc6fb9c）为服务器主线，并以其为基线合并

**背景**：四方版本不一致，需要回答"哪个分支代表服务器"。可选做法有三种：看提交时间、
看提交图上的领先数、看文件内容哈希。

**选择**：按内容哈希。主工作树里 6 个未提交文件与 `dc6fb9c` **逐字节相同**
（`metrics.py` 67,447 字节等），而 `main`（784fc74）里是旧版（42,297 字节）。

**理由**：提交时间会被 rebase 和 checkout 污染；领先数只说明分叉了多少次，不说明谁新。
内容哈希是唯一能直接证明"这份文件就是那一份"的证据。另有一条旁证：对账 spec 里记录的
`recorded base = dc6fb9cf…` 与 `server-mainline` 的 tip 一致。

**执行**：`git merge dc6fb9c` 到 `codex/server-mainline-merge-20261112`，三处冲突：

| 文件 | 处理 | 理由 |
| --- | --- | --- |
| `.gitignore` | 两边都留 | 忽略规则是并集，删任何一条都会让文件重新变脏 |
| `metric_registry.py` | 取 `--theirs` 再加回 adv-excess 声明 | 服务器版是我们的超集，但缺 adv-excess 那一条 |
| `student_runner.py`（add/add） | 取 `--ours` | 我们的版本把 `None` 的 `checkpoint_epoch` 归一化成 `""`，服务器版保留 `None`，会让续跑键对不上而重复计算 |

**后果**：`pytest tests -q` = **225 passed, 2 skipped**（合并前 103 passed）。
合并后主线代码比 `main` 完整，`main` 不再被当作代码基线。

## D-009 修正 D-008：代码主线是 `893a994`（strict-e37），`dc6fb9c` 只是服务器基线提交

**背景**：D-008 用"主工作树 6 个未提交文件与 `dc6fb9c` 逐字节相同"认定 `dc6fb9c` 是主线。
这个推理只证明"那 6 个文件来自 `dc6fb9c`"，不证明"`dc6fb9c` 是最新代码"。
把 9 棵树的文件全部展开后，`strict-metrics-e37`（`893a994`，2026-10-09）的 `metrics.py`
是 76,626 字节 / 56 个顶层函数，而 `dc6fb9c` 是 67,447 / 51 个。

**选择**：判定 `893a994` 为代码主线，并把它合并进整理分支（`92c5d10`）；
`dc6fb9c` 的定位改为"服务器基线提交"。判据用**函数集包含关系**（`ast` 解析后比较函数名集合），
不用字节数，也不用提交时间。

**理由**：
1. 字节大不代表代码新——注释、换行、无关重构都能撑大文件。函数集是严格超集才说明"新代码包含旧代码"。
2. 提交时间会被 rebase / checkout 伪造。实例：`dfc67f2`（activation-survival）提交最晚（10-31），
   但它的 `metrics.py` 只有 43,562 字节 / 33 个函数，底子是 9 月那一版；按时间判会把它当主线。
3. `893a994` 无论按函数集还是按业务内容（e36/e37 指标、strict release 流水线）都是最全的一支。

**执行**：4 处冲突全部取 `893a994` 侧，并补回 adv-excess 声明与其 eligibility 行
（`metric_eligibility.py` 的 `validate` 要求注册表里的每个指标都有资格行，缺一行就 3 个测试变红）。

**后果**：`pytest tests -q` = **284 passed, 2 skipped**。D-008 的合并保留，因为它记录的是
"服务器基线 = 哪一版"这个仍然有效的事实，只是不再等于"最新代码"。

## D-010 三个"补丁级"取舍：egg-info 拒绝入库、matplotlib 降为可选依赖、log 文件入库

**背景**：把剩余的 worktree 独有文件并进来时，有三类文件需要当场定规则，否则会一边漏一边脏。

**选择**：
1. `tools/repository_policy.py` 增加规则：路径里出现 `<package>.egg-info/` → `reject`。
   它是 `pip install -e .` 生成的产物，记录的是**这一台机器**的安装路径，进 Git 只会泄露本机路径。
2. `pyproject.toml` 增加可选依赖 `plot = ["matplotlib"]`，
   `tests/test_e37_diagnostic_plot.py` 改为 `pytest.importorskip("matplotlib")`。
3. `outputs/e28_capacity_family/rb20*_run.log`、`outputs/e34_nb201_pgd1_run.log` 入库。

**理由**：
1. egg-info 是唯一让 `three-space` 看起来还有"5 个独有文件"的东西，拒绝后归零。
2. 只有画图脚本需要 matplotlib，指标流水线不需要。把它设成硬依赖会让服务器环境安装变重；
   设成可选又会让测试在没装的机器上红。`importorskip` 是标准做法：跳过是"环境不具备"，
   失败是"代码有问题"，两者不能混。
3. 运行日志是**实验档案**，不是缓存：它记录当时跑的哪条命令、多少轮、有没有报错，
   丢了就无法复现"这个数字是哪次跑出来的"。三个文件合计 17 KB，属于应入库的小结果。

**后果**：`pytest tests -q` = **477 passed, 3 skipped**（3 skip = 2 个符号链接 + 1 个 matplotlib）。

## D-011 用"全新 clone 能跑通"来证明 GitHub 分支可信，而不是"本机跑通"

**背景**：本机有 9 个 worktree、共享一个 `.venv`（editable 安装还指向主工作树）。
在本机跑 `pytest` 通过，**不能**证明 GitHub 上那条分支是完整的——它可能悄悄依赖了
某个 worktree 里未提交的文件，或者依赖了 `.venv` 里的本地状态。这正是本任务最该防的失败模式：
"本地看着齐全，别人 clone 下来跑不起来"。

**选择**：把 `git clone --depth 1 --branch <branch> https://github.com/SupCE-moon/RobustNASMetric.git`
到一个临时目录，设 `PYTHONPATH=<clone>/src` 后跑 `pytest tests -q`，把结果当作分支是否自洽的判据。

**实测**（2026-11-12）：727 个文件 / 21.75 MiB，最大单文件 1.76 MiB（`search_trials.csv`），
无权重/二进制；`477 passed, 3 skipped in 103.15s`。

**理由**：clone 出来的是"别人拿到的东西"，不含本机任何未跟踪文件、不含 `.venv`。
它跑通才说明源码、配置、测试三者闭合。用 `--depth 1` 是为了快，不影响这个判断
（只检出一个提交，恰好就是要交付的那一版）。

**后果**：以后每次阶段交付前都跑一次这个检查，写进 `docs/PROJECT_STATUS.md`。
文件数 727（clone）与 738（本机 `git ls-files`）的差，是被 `.gitignore` 排除的生成物，不是缺失。

## D-012 本地 1.1 GiB 产物也建 manifest，即使它们永远不进 Git

**背景**：`outputs/` 里有 422 个文件、1,107.2 MiB（含 1 GB holdout checkpoint、18 个对抗缓存）。
它们按策略不入库，但"不入库"不等于"不用管"——报告里的数字要能追到具体文件。

**选择**：用 `tools/inventory_tree.py` 对主工作树 `outputs/` 做全量 SHA-256（无采样），
产出 `results/manifests/local/outputs-inventory.json` + `README.md`，**入库的是清单不是文件**。

**理由**：
1. 清单里有绝对根路径，所以别人（或半年后的自己）能确定"这个哈希对应哪台机器哪个目录"。
2. 1,107 MiB 全量哈希耗时可控（几分钟），换来的是一张能查"这个 1 GB checkpoint 到底是哪一版"的表。
3. 512 MiB 以上才采样会掩盖"同名不同内容"的风险，而 checkpoint 恰恰最容易同名不同内容。

**后果**：清单入库（commit `67b5e74`），文件本体继续留在服务器/本地，符合"GitHub 只存小型结果"的约定。
被策略判为 `reject` 的 22 个文件在 README 里逐个列出，没有静默丢弃。

## D-013 复算工具独立实现，并且必须有行数守卫

**背景**：2026-11-12 服务器 SSH 仍不可达，但需要回答"84 项榜上的名次是真的吗"。
最省事的做法是 `import robust_metric_lab.strict_ranking` 再跑一遍——但那是**用同一份代码自证**：
如果排序或方向处理里有个 bug，两边会一起错，比较结果永远"一致"，什么也没验证。

**选择**：
1. `tools/verify_strict_ranking.py` 用约 40 行 pandas/scipy **重新实现**冻结协议
   （逐 setting 算 Spearman → `direction=="lower"` 取负 → 八设置平均 → 均值降序、名称升序），
   不 import 项目源码。协议常量抄自文档，不抄自代码。
2. 加 `EXPECTED_ROWS`（rb40=40、nb201=64×5、darts=100×2）行数守卫：某个 metric 在某 setting 的
   `ok` 行数不等于网格规模，就**排除该指标并记原因**，不允许"能算出相关系数就算数"。
3. 比较容差 1e-9。

**理由**：
1. 独立实现才有信息量：两条独立代码路径给出同一个数，才叫复核。
2. 行数守卫是被测试逼出来的。第一版只判断"样本够不够算 Spearman"，测试里删掉一行后该指标
   仍然算出 rho=1.0、静默通过；而冻结协议遇到行数不足会整指标排除。不加守卫，工具会把
   "数据缺了一块"的指标算成一个漂亮的相关性——这正是最危险的假阳性。加上守卫后，两个 RACL
   指标被精确判为"0/40、0/64、0/100 ok 行"，与官方"证据不足排除"的理由一致。
3. 1e-9 比浮点求和顺序带来的 1e-16 级差异宽，比"真有问题"的差异严。

**后果**：83 项逐值最大绝对误差 `0.000e+00`、名次顺序完全一致；
第 84 项 `feature_adv_excess_centered_unit_l2` 的原始行只在服务器，明确记为"离线不可复算"，
不假装覆盖。

## D-014 用"指标两两相关矩阵"衡量榜单的冗余度，而不是逐项看名次

**背景**：严格榜上有 84 项，报告里逐项列了名次。但"84 项"这个数字本身会制造一种错觉，
好像有 84 份独立证据。实际上很多指标是同一种测量的变体（例如
`feature_measure_robust_hybrid_delta` 与 `feature_measure_robust_hybrid_rel_delta`）。
如果榜单其实由五六个信号支撑，那么"84 项"就是同一个结论被数了 84 遍。

**选择**：新增 `scripts/analyze_metric_redundancy.py`，在**模型之间的排序**上衡量指标两两的
Spearman 相关，八个设置平均后用平均连接聚类，并在报告里同时给出 ρ ≥ 0.40 / 0.50 / 0.60
三档的簇数。

**理由**：
1. 直接回答"有几个独立信号"，比再列一遍名次更有信息量，也是审稿人会问的第一个问题。
2. 相关算在"排序"上，而不是原始数值上：榜单的用途就是排序，Spearman 与结论的用途对齐。
3. 给三档阈值而不是一档，因为"簇数"依赖切树高度；写下单一数字等于把一个人为选择伪装成事实。

**实现上的两个坑**：
1. `np.fill_diagonal(avg.values, 1.0)` 改的是副本，对角线仍是 NaN，`linkage()` 直接报
   "condensed distance matrix must contain only finite values"。改成 `np.fill_diagonal(mean, 1.0)`
   作用在 `np.nanmean` 的返回值上才对。
2. 覆盖不足的指标（`racl_fixed_network_log_upper_proxy` 只有 1/8 个设置、
   `racl_arch_lipschitz_log_upper` 只有 7/8）不能被当成"相关系数很低"。
   它们在报告里单独列一节并在表里加 `⚠n/8` 标记：只有 40 或 100 个模型支撑的相关系数，
   与 560 个模型的指标不可直接比较。**"没有数据"和"数值低"必须分开写。**

**后果**：ρ ≥ 0.5 时 21 簇，最大簇 35 个（全是特征漂移变体），TRNAS 三项自成一簇，
`jacobian_effective_rank` 与主流负相关。这条只作为"描述性事实"记入 PROJECT_STATUS，
不写成"Φ 更好是因为它独立"——那需要增量检验，是待验证假设。

## D-015 把"文档里的数字"当成需要被检查的对象，而不是可信输入

**背景**：这个项目里同一个结论会在 `PROJECT_STATUS.md`、`docs/experiments/*` 报告、
交接笔记里各写一遍。每写一遍都可能抄错一位小数，或者不小心引用了已经作废的 80 项版本。

## D-022 RB40 的结论一律配置信区间；"排反"的说法已撤回

**背景**：D-021 记录了"八设置平均其实是 NB201 平均"，并给出 RB40 上的点估计
（`trnas_r_score` −0.184、`trnas_activation_psi` −0.194）。当时这些只是 40 个模型上的
单个 Spearman 值，我据此外说过"R-Score 会把模型排反"。这是过度解读。

**做法**：`tools/bootstrap_rb40.py` 按**模型**重采样 2000 次（种子 20261112），
给每个指标的 RB40 相关系数和名次都配上 95% 区间，并给"RB40 排名 vs 发布榜"的
Kendall τ 也配上区间。阈值 `REPRODUCTION_TOLERANCE = 5.5e-4`：发布表只存三位小数，
重算与表的最大差不可能小于半步，用 1e-6 判会把 84 个指标全判成"不一致"。

**结果与更正**：
- Φ +0.576 [0.310, 0.761]、`adversarial_loss` +0.743 [0.487, 0.903] → 稳定正相关。
- `trnas_r_score` −0.184 [−0.459, +0.136]、`trnas_activation_psi` −0.194 [−0.471, +0.128]、
  multiview max +0.302 [−0.030, 0.589]、RMS +0.226 [−0.119, 0.521] → **区间跨 0，方向不确定**。
- τ(RB40, 发布榜) = −0.143 [−0.243, +0.018] → **不能断言反向，只能说两套排序不一致**。

**选择**：把"方向不确定"写进结论，撤回"排反"的表述；同时**保留点估计**，
因为它与发布表逐位吻合（最大差 0.000499 = 三位小数舍入），是数据本身，不是噪声。

**理由**：
1. **区间跨 0 就是不知道方向**。说"该指标在已训练模型上失效"和说"它有效"一样没有依据。
   用"没有证据"代替"证明了没有"，是这套口径的底线。
2. **名次区间比点名次有用**。R-Score 的名次区间是 37–81，此时说"第 73"是假精度。
3. **重采样单位必须是模型**。40 个模型 × 84 指标 = 3,360 行，但独立单元只有 40 个；
   按行重采样会把区间算窄、把 p 值算小。

**后果**：`docs/PROJECT_STATUS.md` §3 第 11 条换成带区间的表；`docs/ROADMAP.md` §8
把 bootstrap 标为已完成，"分网格榜"降为可选。"要分辨 R-Score 方向"现在是一条
**需要更多模型**的数据需求，不再是分析需求——这一条要写进第二阶段的数据计划。
**两个 τ 为什么不同**：`analyze_setting_weights.py` 报 τ(RB40, 发布榜) = −0.127，
本工具报 −0.143。差别来自输入：前者用表内三位小数的 `rb40_mature` 列，
后者用原始行全精度值重算、并合并了 TRNAS 的三行修复。0.016 的差在并列处理与舍入的量级内，
两个区间都跨 0，结论一致。**引用时用带区间的 −0.143**，因为它说明了不确定性。
## D-023 Φ 的增量检验按预注册判据执行，结论是"有增量"；机制仍未回答

**背景**：D-019 定下了检验方案与判据（"先定判据后看结果"），方案文件
`docs/experiments/增量检验方案_Φ对特征漂移族_20261112.md` 里写了 T1/T2/T3 三个检验、
按 204 个架构聚类的区间、以及预先写死的判定表。之后用户连续多轮未回复三个待批准问题，
而 goal round 在继续推进。

**决定**：执行，不擅自改判据。

**理由**：这个检验只重读已入库的冻结原始行——不训练模型、不动发布表、不改冻结协议，
而且它回答的是"我自己上一轮的结论是否被替代解释推翻"。判据先写死正是它有价值的原因；
若等批准再跑，判据就有被结果影响的空间。脚本参数全部可复现（种子 20261112、
`--resamples 2000`），用户若要求换基准口径，重跑即可，不需要重写结论。

**实现中的三个要紧处**：

1. **架构身份必须带网格**。DARTS 与 NAS-Bench-201 都把架构编号成 0..N，最初用裸 id
   导致 `darts:0` 与 `nb201:0` 被当成同一个网络（`n_architectures` 是 203 而不是 204），
   bootstrap 会把两个无关网络一起抽。改成 `grid:id` 后修正。
2. **方向必须按注册表翻转**。漂移族声明 `lower`（漂移越小越好），不翻转时
   `ρ(B,y) = −0.831`，看着像"漂移越大越鲁棒"。翻转后 B 与 target 同向。
3. **置换检验的 p 值要加一**。用 `(超出次数+1)/(B+1)`，因为 B 次置换能达到的最小 p 是
   `1/(B+1)`；报 0.0000 会比设计允许的精度更绝对。最终 p = 0.0005（2000 次里 0 次超过）。

**结果**：Δρ = +0.695，区间 [+0.583, +0.769]，p = 0.0005；嵌套模型 R² 从 0.163 升到 0.640
（增量 +0.476）；同漂移分位内的秩相关 +0.637。两个稳健性对照给出 0.685（PCA）与 0.676
（每设置挑最强的单个族成员，乐观上限）。

**关键解读（写进报告，避免误读）**：Δρ 高有两个来源，必须分开说。
在 RB40（ρ(B,y) = −0.125）与 DARTS e100（−0.028）上，漂移族平均几乎不预测鲁棒性，
控制一个无效变量等于没控制，偏相关退化成 ρ(Φ,y)——那里的高值**不是**"Φ 增量大"。
真正有说服力的是 `nb201_e0`：B 与 target 的相关 0.831、Φ 与 B 共线 0.823，
在这种最难分的条件下 Δρ 仍有 0.522。

**可以说的**：Φ 不是 35 个漂移指标的另一种写法。
**不可以说的**：Φ 更好是因为它测"一致性"而不是"幅度"——那是机制解释，本检验不涉及；
更不能说因果。

**后果**：`docs/PROJECT_STATUS.md` §3 第 12 条、§4 合理推断段更新；
`docs/ROADMAP.md` 的 RQ1 证据状态升级；第 6 轮汇报里"Φ 可能只是漂移族变体"的猜测被否定，
这一点要明确告诉用户。

1. **用 AST 静态解析，不 import 模块**。审计的价值之一是能在只有 pandas 的机器上跑
   （读发布 CSV 的那台机器），而 `metrics.py` 一 import 就要 torch。
   代价是必须处理注册表的两种写法：直接 `MetricSpec(...)` 和 `_specs((...), ...)` 批量声明；
   只扫字面量会漏掉 39 个（首版就漏了，86 报成 47）。
2. **NaN 要分两类**。`perturbation_capacity_importance_delta` 在 bundle 里是 `float("nan")`，
   这是**设计**：它需要两遍法的重要性向量，入口在 `importance_batched.py`。
   另一类"非有限且没有任何其他入口"才是缺陷。两者混在一起报，会让真正的缺陷淹在噪声里。
3. **`registry only` 必须返回退出码 1**。这条检查的全部价值在于它会失败；
   一个永远返回 0 的审计等于没有审计。

**已知的 1 个 `registry only`**：`feature_adv_excess_centered_unit_l2`。
它的公式在 `adv_excess_metric.py` 里（`_unit_centered` + `adv_excess_per_sample`），
但**没有任何代码把这个字符串写成输出键**。这与"它的原始行只存在于服务器、
离线无法复算"互相印证：生产它的脚本大概率留在了服务器上，没有进仓库。
**不擅自补一个实现**：那等于在没有原始行的情况下编造一个可能与被发布数字不同的算法。

**测试里为什么留了一条绑定真实数据的断言**：`test_real_registry_has_no_unimplemented_metric`
断言 `registry_only == ["feature_adv_excess_centered_unit_l2"]`。这看起来脆弱，
但它的作用是让"这个洞被补上了"这件事必须显式改测试——而不是悄悄消失。
注释里写了补上之后该删哪一条断言。

**后果**：`docs/PROJECT_STATUS.md` §3 第 13 条、§6 第 5 条更新；
`results/audits/metric-implementation-20261112.{json,md}` 可随时重建。

## D-025 —— 用"物理不变量"代替人肉读代码来评审指标实现（2026-11-12）

**背景**：`docs/PROJECT_STATUS.md` §6 挂着"571 行指标代码未做逐行数学评审"。
571 行逐行读，代价高、且读到第三十个函数时注意力已经不可靠。

**决定**：先跑一层**自动化的最低要求检查**（`tools/audit_metric_invariants.py`），
只问三个不需要判断"指标是否有意义"的问题：距离在零扰动时是否为 0、是否处处有限、
是否随扰动增大而增大。把"需要人读代码的地方"从 571 行压缩到 1 个被标记的指标。

**四条选择与理由**：

1. **用两层卷积小网络，不用 resnet18**。审计要在任何机器上半分钟内跑完，
   否则没人会在改完指标后跑它。代价必须写在报告里：结论只对"这一个随机小网络"成立。
2. **只用 FGSM 的梯度符号，不调攻击库**。这里要的是"可控的扰动强度扫描"，
   不是"最强的攻击"；符号梯度给出恰好 `eps` 的 L∞ 位移，便于检验单调性。
3. **`decreasing` 不算失败，但必须报**。符号约定与实现错误是两回事；
   把它判成 failure 会逼着人立刻改注册表，而改注册表等于改历史（D-021 的先例）。
   现在是"报出来 + 挂进 §6 待确认"，不是"静默通过"。
4. **测试里留一条绑定现实的断言**。`test_real_bundle_flags_signed_capacity_delta_as_decreasing`
   断言的是当前事实而非期望性质。与 D-024 同理由：结论变化必须显式改测试。

**踩过的坑（已固化成测试）**：第一版探针写 `g.detach().sign()`，拿到的是全零的输入占位张量，
于是七个 epsilon 得到七行相同的 0，看起来像"所有指标恒为 0"。
正确写法是 `g.grad.sign()`。这件事说明：审计工具本身必须先被审计，
所以 `test_fgsm_sign_is_unit_and_not_all_zero` 断言符号张量非零。

**batch 敏感性**：4 张图时 `signed_capacity_delta` 判为 `unordered`，6 张图时判为 `decreasing`。
测试用 6 张（与 CLI 默认一致），并把这个敏感性写进 fixture 注释——它本身是关于该指标的信息。

**后果**：§3 第 14 条、§6 第 0 条、`results/audits/metric-invariants-20261112.{json,md}`。

## D-026 —— 有符号与绝对 capacity 漂移是两个指标，不是同一指标的符号版本（2026-11-12）

**背景**：D-025 的审计发现 `perturbation_capacity_signed_delta` 随扰动增大而单调变负，
与它注册的 `lower` 方向相反。而 `metrics.py:1265` 与 `:1286` 显示它和
`perturbation_capacity_delta` 只差一个 `abs()`，所以最自然的读法是「同一个指标，换个符号」。

**决定**：用已发布的 560 行原始数据核对这个读法，结论是不成立——两者在设置内的秩相关
中位数只有 +0.017，4/8 个设置里它们与 target 的相关符号相反，而配对自检
`|signed| <= abs` 在 560 行上零例外（两列确实来自同一批样本）。

**为什么这件事值得单独记一笔**：

1. **两条都在榜上**。如果读者以为它们是同一指标的正负版本，就会把两个名次当成两次独立验证；
   实际上 signed 度量「方向净额」（上升样本抵消下降样本之后的余量），abs 度量「幅度总额」。
   抵消程度逐模型变化极大，所以两者排序几乎无关。
2. **不能因此判断哪个更好**。本轮没有控制模型容量，也没有区分「符号约定」与「分母效应」
   （鲁棒模型的 clean capacity 更小，同样的绝对下降会被放大）。所以 §6 第 0 条只划掉一半，
   偏秩相关的后续检验仍挂着。
3. **这不是新发现，而是把旧观察变成可复跑的审计**。`scripts/analyze_e32_generality.py`
   的 docstring 早就写过 unsigned 丢掉符号结构、会在 NB201 e5 翻转；此前没有人把它量化到
   榜单层面，也没有配对自检。审计的价值在于「下次改动后能重跑并立刻看到是否还成立」。

**踩过的坑**：把含中文的 Python 补丁脚本经 PowerShell here-string 传给 `Out-File -Encoding utf8`，
导致整个工具文件写成乱码（U+FFFD），而且脚本里英文双引号包中文还造成语法损坏。
**教训**：含中文的文件一律用 write 工具写；中文引号一律用「」；脚本里不要把中文放进英文引号中。

**实现里两个会影响结论的细节**：

- `load_panel` 必须**先 repair 再 dropna**，且 `pivot_table(dropna=False)`。否则
  `repair_rows.csv` 要补的行在合并阶段就被删掉——恰好删掉本次要看的指标（与 D-022 同一个坑）。
- `summarise` 里加 `abs_le_abs_violations` 配对自检。它是数学恒等式，一旦不为 0 就说明
  两列不是同一批样本，此时上面所有结论都无意义。测试用「伪造一行 |signed| > |abs|」守住它。

**后果**：§3 第 15 条、§6 第 0 条、`results/audits/signed-capacity-20261112.{json,md}`、
`tools/audit_signed_capacity.py`、`tests/test_audit_signed_capacity.py`（8 个测试）。
## D-027 —— 用一条命令跑完全部审计，而不是把 11 条命令写进交接文档（2026-11-12）

**背景**：到这一轮，审计脚本已经有 11 个。每多一个，交接时的「跑一下自检」就多一分走样：
参数名不同（`--rows` / `--table` / `--ranking` / `--redundancy`），
把原始行传给 `--table` 通常不会报错，只会算出一个看起来合理的数。

**决定**：`tools/run_audit_suite.py` 把参数接线写进代码，按依赖顺序执行，
产出一张「通过 / 失败 / 跳过」的表。

**五个选择与理由**：

1. **顺序由依赖决定，不由方便决定**。`redundancy` 的输出是 `phi_incremental` 的输入，
   顺序错了会拿上一轮的聚类去算这一轮，结果仍能跑通——这类错误最难发现，所以写死在列表里。
2. **`skipped` 与 `ok` 分开计，且报告里明说「skipped 不是通过」**。7 个步骤依赖那份
   13.9 MiB 的原始行，而它按策略不入库。如果不区分，一台干净 clone 上会显示「11 项检查全部通过」，
   这是最糟的结果——检查没跑，报告说通过。
3. **允许的退出码按步骤配置**。`implementation` 与 `signed_capacity` 用退出码 1 表示
   「有一个需要人看的结论」，把它当崩溃就会逼着人忽略它；把它们当 0 又会掩盖真崩溃。
   所以每步显式写 `expect_exit`，并在报告里仍然打印退出码。
4. **`--rows-root` 三级回退**（参数 → 环境变量 → `git worktree list` 的主工作树）。
   第三级让「干净 clone 也能跑」，代价是它可能悄悄用了另一棵树的 `outputs`，
   所以报告开头打印实际使用的路径，而不是假装用了仓库内的文件。
5. **不重算任何数字**。suite 只负责跑和汇总；每个数字仍由它原来的脚本产出，
   报告链接到原报告的路径。否则一旦有人改判据，就会出现「suite 的数和报告的数不一致」。

**顺带修的自污染**：`check_doc_links.py` 原来只跳过 `doc-links-` 前缀，
没覆盖 suite 用的无日期 `doc-links.md`，导致上一轮的缺失清单被当成新引用重复计入（25 条假断链）。
改为按前缀集合跳过，并补了「人写报告仍要扫」的反向测试，避免把规则放宽到看不见真问题。

**后果**：`tools/run_audit_suite.py`、`tests/test_run_audit_suite.py`（9 个测试）、
`results/audits/audit-suite.{json,md}`、§3 第 16 条、`docs/HANDOFF.md` §19。

## D-028 —— 用现成的 RobBench 数据做 RQ2 的第一次检验（2026-11-12）

**决定**：RQ2 的第一步不训练模型，而是用官方 NAS-RobBench-201 发布里已有的
「训练后鲁棒准确率」，与仓库里已有的 64 个架构 e0 指标做相关分析。

**为什么**：ROADMAP 原先排的是「16 架构 × 3 seed 训练 6–10 天」。但 RobBench 已经给出
6466 个架构在固定协议下的 `val_acc` / `val_pgd_8.0_acc` / `autoattack`，且已有的 64 个 e0
架构 64/64 全部能对上。在花训练算力之前先问「有没有任何信号」，是更便宜的验证顺序；
而且这份数据是别人发布的，不受我这边训练噪声影响，不会出现「自己训练自己评估」的循环。

**为什么必须控制 clean 准确率**：在这份数据里训练后 clean 与 AutoAttack 的秩相关是
**+0.982**。这意味着「能预测 clean 准确率」几乎等价于「看起来能预测鲁棒性」。
不控制它，任何测「这个架构好不好训」的指标都会被误读成鲁棒性预测器。所以每个指标都报
三列（原始相关、与 clean 的相关、控制 clean 后的偏相关），并以**偏相关**作为判定依据。

**为什么判定分五级**而不是一刀切：

- `direct`（偏相关 ≥ 0.30）：控制后仍站得住，这是 RQ2 想要的证据。
- `via_clean`（原始 ≥ 0.30 但偏相关 < 0.10）：它预测鲁棒性的方式是预测 clean 准确率。
  这不是「没用」，但用来谈抗攻击能力就是错的。
- `suppressed`：控制后符号翻转，说明原始相关是被 clean 反向混杂压出来的（例如
  `jacobian_effective_rank` 原始 −0.487、偏相关 +0.565）。这类指标最容易被误读成「越差越鲁棒」。
- `weak` / `uncovered`：两边都弱，或可用样本不足。
  分级本身是判断，所以阈值（0.30 / 0.10）写在代码常量里并由测试固定，事后不改。

**为什么按架构 bootstrap**：n=64 是 64 个架构，不是 560 行；按行重采样会把区间算窄。

**为什么不说因果、也不说「可以替代训练」**：

1. 早期指标来自本仓库的 e0 前向，target 来自 RobBench——两者的**流程**不同，但目标本身与本仓库
   的 `oracle_target` 是同一份数据（见下面的更正）。只能说「架构层面的早期指标与训练后结果相关」，
   不能说「训练早期就能预测」。
2. 只有一次初始化，初始化噪声完全没估计。
3. 只有 64 个架构，Spearman 的 95% 区间约 ±0.25。
4. 控制 clean 只排除了一条混杂路径；参数量、可训练性、RobBench 自身协议差异都还在。

**更正（2026-11-12 同日补做 target 同源核对）**：上面第 1 条最初写成「跨协议比较」，并把
「两套 target 可能矛盾」列为首要局限——这是**说反了**。核对 `outputs/e28_capacity_family/nb201_e0_v3.csv`
的 `oracle_target` 与 RobBench 的 `autoattack`（threeseed，按 arch_id 对齐）：64/64 匹配、
秩相关 +1.000、最大绝对差 0.00e+00，**是同一份数据**。因此：

- 不存在「两套 target 互相矛盾」，target 的选择没有引入额外不确定性；
- 真正的局限是**只有一套 target**，没有第二套独立结果可做外部验证；
- 需要保留的谨慎只剩「早期指标是随机初始化网络的一次前向，目标是固定训练协议的结果」，
  这是流程差异，不是数据矛盾。

脚本因此新增可选 `--oracle-table`：提供时在报告里自动做这项核对，并按结果二选一措辞
（「同一份数据，局限是只有一套 target」/「不是同一份数据，target 选择本身是不确定性来源」）。
`run_audit_suite` 在 `outputs/e28_capacity_family/nb201_e0_v3.csv` 存在时自动传入，不存在时
该步骤仍能跑，只是不报同源核对。

**后果**：`scripts/audit_early_metrics_vs_robbench.py`、
`tests/test_audit_early_metrics_vs_robbench.py`（16 个测试，含同源/不同源两组）、

## D-029 —— 扩到 400 个架构，并用同一配方重跑 64 个作为对照（2026-11-12）

**背景**：D-028 的 RQ2 检验只有 64 个架构，Spearman 的 95% 区间约 ±0.25，无法判断 +0.5 的偏相关

**决定**：用 e27 的 zero-cost 配方给 400 个架构算 e0 指标，并且**先用同一配方重算已发布的 64 个**

**为什么必须先重算 64 个**：只比较「发布表的 64」和「新算的 400」，会把两种差异混在一起——
样本量变了，数据来源也变了。重算 64 个之后，`当前代码 64 → 当前代码 400` 只变了样本量，
`发布表 64 → 当前代码 64` 只变了数据来源。这两条对照给出的答案不一样：
前者最高偏相关都是 +0.357（只是区间收紧），后者是 +0.575 → +0.357（幅度明显下降）。

**结论怎么改**：RQ2 的正面证据从「+0.5 量级」下调为「约 +0.35，400 架构上区间不跨 0」。
这不是推翻，是把幅度改到能在两个口径下都成立的数。**下调的理由是数据源差异，不是样本量效应**，
这一点必须写在报告里，否则下一个人会以为「扩大样本后信号变弱了」。

**发现的数据问题**：发布表的 `nb201_e0` 与当前代码重算的值不一致（`feature_delta` 差约 20 倍，

## D-030 —— 把参数量作为 RQ2 的第二个混杂控制进去（2026-11-12）

**背景**：D-028/D-029 只控制了训练后 clean 准确率。参数量是更明显的候选：更大的架构可能既漂移得多、
又训练得准。RobBench 的 `meta.json` 没有参数量，但 C=16/N=5 的 tiny 网络参数量可由 op 组合直接算出来。

**决定**：用 `Nb201TinyNetwork(ops)` 的实际参数个数（不是估计值）作第二控制变量，做三方偏秩相关
（秩化后对「截距 + clean + params」回归取残差），并按架构 bootstrap 2000 次给区间。

**结果与解读**：参数量确实与 target（+0.710）、clean（+0.692）强相关，但**控制它之后信号没有消失、
反而略升**（最强的 `feature_delta` 从 +0.371 到 +0.422）。判定分布
survives 12 / shrinks 7 / explained_by_capacity 5 / weak_before_capacity 45。

**为什么"反而升高"不能当成好消息**：这通常意味着控制变量是**抑制变量**（与 clean 同向、与指标不同向），
去掉它等于去掉了指标里与 target 无关的那部分变异。所以这不是"更强的证据"，而是"更干净的对照"。
报告里写死了这句解释属于推断，不是机制。

**判定桶为什么多一个 `weak_before_capacity`**：`rho_clean` 本来就 < 0.30 的指标，谈不上"被参数量解释"。
初版把它们算进 `explained_by_capacity`，导致 47 个指标被误标——真正的「被解释」只有 5 个。
这个桶是测试 `test_classify_separates_weak_from_explained` 逼出来的。

**代价**：每个指标要跑 2000 次两控制偏相关（400 架构），单次全量约 6 分钟；可以用 `--resamples` 降。

**后果**：`scripts/audit_rq2_confounders.py`、`tests/test_audit_rq2_confounders.py`（12 个测试）、

## D-031 —— 发布表 e0 的列按「代码上界」判定能否引用（2026-11-12）

**背景**：D-029 记录「发布表 e0 与当前代码不一致」，当时只比了一列、只给了范围与秩相关。
这一轮把它做成逐列核对，并且把判据从"人挑一个阈值"换成**代码自己的上界**。

**判据**：`src/robust_metric_lab/metrics.py:745` 的 `... .clamp_max(1e3)` 把相对类特征指标卡在 1e3。
这个 clamp 在 `dc6fb9c`、`410184e`、`HEAD` 三版里都有。所以发布值 **> 1e3** 就不是本仓库代码能产出的。
这条判据可审查、可复算，不依赖任何主观口径。

**结果**：70 个共有指标里 `clean` **0 个**、`spiked` 14 个、`divergent` 55 个、`uncomparable` 1 个；
秩相关中位数只有 0.338，最高 0.772。

**决定**：
1. **第 17 条那批数字作废**（Φ 的 +0.170、`feature_spectral_participation_ratio_static` 的 +0.575、
   `feature_measure_swd` 的 +0.512）。不是因为方向错了，而是因为**输入无法被独立验证**。
   RQ2 的量化结论统一以第 18、19 条（当前代码重算）为准。
2. **不改发布表、不重算它**：它是那次流水线的真实输出，`release_verification.json` 的 PASS 也是真的。
   问题在"那一版代码不在本仓库历史里"，改表等于替别人重写历史（D-021 的同一条理由）。
3. **判据写进工具**，以后任何人想引用发布表 e0，先跑 `tools/audit_published_e0_sanity.py`。

**为什么不把 `divergent` 也叫"错"**：秩相关 < 0.8 说明的是"同名不同量"，这是两个实现之间的差异，
不是错误。只有 `spiked` 那 14 个能确定"本仓库代码产不出来"。

**后果**：`tools/audit_published_e0_sanity.py`、`tests/test_audit_published_e0_sanity.py`（9 个）、
`results/audits/published-e0-20261112.{json,md}`、`docs/PROJECT_STATUS.md` §3 第 17 条加更正框、
§3 第 20 条、§4 把那条从"已验证事实"降级为"作废"。
## D-032 —— 偏相关必须把控制变量也秩化，RQ2 的信号随扰动口径变化

**背景（两件事撞在一起）**：这一轮本来是给 RQ2 补"扰动敏感性"，结果在核对基准列时发现
**同一个仓库里两个"偏秩相关"实现给出相差三倍的结果**：
`audit_rq2_confounders.partial_rho` 只把 x 与 y 秩化，控制列以原值进回归；
`audit_early_metrics_vs_robbench.partial_spearman` 则把控制列也秩化。
对同一个指标（`feature_delta`，400 架构，控 clean + 参数量）前者给 **+0.422**、后者给 **+0.145**。

**决定 1：统一为全秩化**。理由：
1. 只有全秩化才是"秩偏相关"的标准形式，且对控制列的任意单调变换不变——这是可检验的性质，
   现在用 `test_partial_rho_ranks_the_controls_too`（把控制列取 `exp` 后结果必须不变）守住。
2. 混着用会让两个审计互相矛盾，而读者只会看到两份都写着"偏相关"的数字。
3. 加了 `test_partial_rho_agrees_with_the_early_metric_helper`，两个实现必须给同一结果。

**决定 2：更正 D-030 的数字，不回避**。`feature_delta` 不是最强的早期信号（只 +0.145，属
`weak_before_capacity`）；最强的是 `feature_measure_robust_delta` **+0.400 [+0.304,+0.478]**；
`survives` 从 12 个降到 5 个，`explained_by_capacity` 从 5 升到 11。已在 `PROJECT_STATUS.md` §3
第 19 条写明"这是口径更正"，不悄悄改数。

**决定 3：做扰动敏感性，并把结论往下调**。同一批 400 架构、同一权重种子，只换扰动：
`base` = FGSM 8/255 单步、`weak` = FGSM 4/255、`pgd` = PGD-3 8/255。结果：
- `feature_measure_robust_delta` 从 **+0.400** 变成 **−0.271 / −0.275**（翻号）；
- 前五名重合 **0/5**，指标级排序相关 **+0.044 / +0.031**；
- 但 `input_grad_l2`（+0.367 → +0.481）与 `margin_input_grad_ratio`（+0.252 → +0.446）方向稳定。

所以"某个指标最好"是**配置的性质**，不是架构的性质。RQ2 的正确表述改成
「存在早期信号，量级 0.3–0.5，但排序随扰动口径变化」。

**为什么不干脆说 RQ2 失败**：因为信号没有消失——控制两个混杂后仍有 5 个指标 |ρ| ≥ 0.30，
且 `input_grad_l2` 在三个配置下都在 +0.37 以上。坏消息是**排名**不稳，不是**存在性**不成立。

**代价**：30 分钟 GPU（400 架构 × 2 变体）。因此**不放进** `run_audit_suite.py`（那里预算是 3 分钟），
只在 HANDOFF 里记为可选重跑。

**后果**：`scripts/audit_e0_perturbation_sensitivity.py`、`tests/test_audit_e0_perturbation_sensitivity.py`
（13 个）、`scripts/audit_rq2_confounders.py` 修 `partial_rho`、`tests/test_audit_rq2_confounders.py`
（12 → 14 个）、`results/audits/e0-perturbation-20261112.{json,md}`、
`results/audits/rq2-confounders-20261112.{json,md}` 按新口径重生成、
`docs/PROJECT_STATUS.md` §3 第 19 条加更正段、新增 §3 第 21 条、§4 两处改写。
