## 2. 两个研究问题，各自的证据状态

### RQ1：已训练防御模型，特征稳定性指标能否预测/排序其真实鲁棒性？

- 现状：**基本已回答，但 2026-11-12 的权重分析改变了读法**。84 项榜给出了八设置下的排序力；Φ 0.782、R-Score 0.738、自研 max 0.524 / RMS 0.495。
  **但八设置平均实际是"NB201 平均"**：与只 NB201 的名次 τ = +0.926，与只 RB40（真正的已训练防御模型）τ = −0.127；
  在 RB40 上 Φ 排 12、`trnas_r_score` 排 73（−0.184，负相关）、`trnas_activation_psi` 排 76，
  而 `adversarial_loss` 排 2、`feature_adv_excess_centered_unit_l2` 排 1。
  所以回答 RQ1 时必须说明是"八设置平均意义下"还是"已训练模型意义下"。
- 剩余缺口有三处：
  1. ~~**Φ 的第一名是否只是漂移族的另一种写法**~~——**2026-11-12 已执行**（M1 完成）：
     控制 35 个漂移指标后 Φ 的偏秩相关仍有 Δρ = +0.695 [+0.583, +0.769]、p = 0.0005，
     嵌套模型 R² 增量 +0.476；在漂移族最强的 `nb201_e0` 上仍 +0.522。
     结论：这个替代解释被排除。剩下的是机制问题（为什么），不是"是否重复"的问题。
  2. **跨协议稳健性**：已量化（`results/audits/setting-weights-20261112.md`），**不确定性也已补上**
     （`results/audits/bootstrap-rb40-20261112.md`，按模型 bootstrap 2000 次）。
     RB40 上 Φ +0.576 [+0.310, +0.761] 与 `adversarial_loss` +0.743 [+0.487, +0.903] 稳定；
     R-Score −0.184 [−0.459, +0.136]、Ψ −0.194 [−0.471, +0.128] 方向不确定。
     要分辨这两个需要**更多模型**，是数据需求而非分析需求。
  3. **分网格榜**：若要对外报"已训练模型上的排序力"，需要一张单独的 RB40-only 榜（含 CI），
     目前只有带区间的指示性数字。

### RQ2：未训练/训练早期的架构，其指标能否预测该架构训练完成后的鲁棒性？

- 现状：**只有相关证据，没有预测证据**。已有的是"同一网格不同训练阶段之间的指标排序稳定性"（Φ 在 NB201 e0 vs e50 秩相关 0.914、DARTS e0 vs e100 0.995），
  这证明**指标本身稳定**，但**没有**证明"e0 的指标能预测训练完成后的鲁棒准确率"。
- 关键差别：指标稳定 ≠ 能预测。一个恒等于 1 的指标在所有阶段都完全稳定，但毫无预测力。
- 这正是本项目最有新意、也最缺的一环。

## 3. 第二阶段：RQ2 的最小可发表实验

### 3.1 设计（一句话）

**取一批架构，只用它们在 e0（随机初始化）的指标排个序；然后把这批架构按固定协议训练到底、用统一攻击测出真实鲁棒准确率；最后看 e0 的排序与训练后的排序是否一致。**

### 3.2 具体参数（冻结后不再改）

| 项 | 取值 | 为什么 |
| --- | --- | --- |
| 数据集 | CIFAR-10，50,000 训练 / 10,000 测试 | 与全部既有实验一致 |
| 架构池 | NAS-Bench-201 全部 64 个架构（先做 16 个的试点，见 3.5） | 已有 64 架构的 e0 指标与权重基础设施 |
| 训练协议 | 对抗训练 PGD-7，100 epoch，batch 256，SGD momentum 0.9，初始 lr 0.1，cosine 退火，weight decay 5e-4 | 与 E23 的 PGD-7 一致，避免"换了协议所以结论变了" |
| 随机种子 | 3 个（20261112 / 20261113 / 20261114） | 单种子无法区分"架构效应"与"训练噪声" |
| 早期指标时刻 | **e0**（随机初始化，不训练任何一步） | 最干净的"零成本"设定；e5 作为次要分析 |
| 预测目标 | 训练完成后测试集上的 **PGD-20 鲁棒准确率**（ε=8/255，步长 2/255） | 与既有网格口径一致 |
| 参照攻击 | 对前 8 名架构补跑 AutoAttack（约 2 小时/架构） | 防止"PGD 过估"把排序弄反 |
| 评估 | 每架构 3 seed 的鲁棒准确率取均值后，与 e0 指标算 **Spearman**；bootstrap 95% CI 按**架构**重采样（不是按 seed） | 与 RQ1 的统计口径保持一致 |

### 3.3 必须做的对照（否则结论不成立）

1. **控制参数量/FLOPs 的偏相关**：e0 指标很可能只是"模型容量"的代理，而容量与鲁棒性相关。
   必须报"控制参数量后"的偏 Spearman——E26/E28 已经证明这一步能推翻结论（capacity 的 0.744 在去混杂后掉到 0.28–0.38）。
2. **随机基线**：把"架构名"随机打乱后算一次，确认 CI 的零点位置。
3. **固定扰动 vs 自生成扰动**：e0 模型的梯度几乎是噪声。**必须**同时报两种口径：
   (a) 用该 e0 模型自己的 FGSM（白盒，噪声大）；
   (b) 用同一批固定扰动（由成熟模型或固定随机方向生成）。
   两种口径若给出相反排序，说明 e0 指标对扰动来源敏感——这本身就是一个值得报告的负结果。

### 3.4 零成本检验：用现成的 RobBench 数据先回答「有没有信号」（**已完成 2026-11-12**）

在准备训练之前发现了一份不需要训练的数据：官方 NAS-RobBench-201 发布
（`.worktrees/activation-survival/data/official_nasrobbench201_source/NAS-RobBench-201_all.json`，
15.6 MiB，按策略不入库）对 **6466 个** NAS-Bench-201 架构给出了训练后的 `val_acc`、
`val_pgd_8.0_acc`、`autoattack` 等结果。已有的 64 个架构 e0 指标 **64/64 全部能对上**。

这一步已经做完（`scripts/audit_early_metrics_vs_robbench.py`，接入 `run_audit_suite` 第 12 步）：

- **陷阱**：这份数据里训练后 clean 与 AutoAttack 的秩相关是 **+0.982**，所以只看原始相关会把
  「能预测 clean 准确率」误当成「能预测鲁棒性」。必须报控制 clean 后的偏相关。
- **结果**：84 个 e0 指标里 28 个仍有 ≥0.3 的偏相关，17 个属于「控制后消失」。
  Φ 的原始相关 +0.849、偏相关只剩 **+0.170**（区间跨 0）；真正站住的是输入敏感性族
  （`input_grad_l2` +0.522、`local_logit_lipschitz` +0.519、`input_loss_delta` +0.536、
  `jacobian_spectral_norm` +0.527）与 `feature_measure_swd` +0.512。
- **它没有替代训练**：只有一套训练协议、单次初始化。M2 把 e0 覆盖扩到 400 个架构后，
  最高偏相关仍是 +0.357（区间收紧到 [+0.260,+0.437]），说明**扩同一批指标**换不来更强的信号。
  但它把「先花 6–10 天训练 16 个架构」从**第一步**变成了**第二步**，而且现在知道第二步该换什么。

### 3.5 试点优先（先花 1/5 的钱验证管道）

先用 **16 个架构**跑通全流程（覆盖架构族：`none`/`skip`/`nor_conv` 主导各取若干，按参数量分层抽样）。
试点只回答一个问题：**管道能不能跑通、e0 指标有没有任何排序信号**（哪怕很弱）。
- 若 e0 指标与训练后鲁棒性的 Spearman 的 95% CI **完全覆盖 0 且宽度 > 0.6**，说明这个设定下预测不了；
  此时**不要**直接扩到 64 个架构，而应先改设计（换早期时刻到 e5、换目标为 PGD-7 训练后的干净准确率等），并把这次失败写进报告。
- 若 CI 下界 > 0.2，再扩到 64 个架构。

### 3.6 算力预算（估算，需实测校正）

| 项 | 单次 | 数量 | 合计 |
| --- | --- | --- | --- |
| 对抗训练 100 epoch（RTX 4080） | 3–5 小时 | 16 架构 × 3 seed = 48 | 144–240 小时（6–10 天单卡） |
| PGD-20 评测 | 10 分钟 | 48 | 8 小时 |
| AutoAttack 评测 | 2 小时 | 8 架构 | 16 小时 |
| 指标计算（e0） | 约 4 秒/模型 | 16 | 1 分钟 |

**结论：试点 16 架构 × 3 seed 是单卡 6–10 天的量级。** 全量 64 架构 × 3 seed 约 25–40 天单卡，
必须先在试点上拿到正向信号、并确认服务器（多卡）可用，再决定是否做。

## 5. 风险与失败模式（先写下来，避免事后解释）

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| e0 指标只是容量代理 | 控制参数量后相关掉到 0 | 预先报偏相关；若掉到 0，结论写"e0 指标无独立预测力" |
| e0 梯度是噪声 | 白盒 FGSM 口径与固定扰动口径排序差很大 | 两种口径都报，不挑好看的 |
| 训练不稳定 | 同架构跨 seed 的鲁棒准确率方差大 | 3 seed，报 seed 间相关；方差大时以 seed 均值为准并说明 |
| 目标被 PGD 过估 | 排序与 AutoAttack 排序不一致 | 前 8 名补 AutoAttack |
| 汇总口径漂移 | 无意中改了聚合顺序，数字与 RQ1 不可比 | 直接 import `tools/verify_strict_ranking.py`，不复制逻辑 |
| 算力不够 | 训练排队、超时 | 先做 16 架构试点，拿到信号再扩 |

## 7. 不做什么（明确排除）

- 不新造指标去刷榜。当前的瓶颈不是"缺一个更强的指标"，而是"不知道早期指标能不能预测"。
- 不把相关性写成因果。所有本路线图的结论都必须带"相关/排序"的措辞。
- 不在没有独立留出集的情况下宣称"泛化到新架构"。留出集冻结方案见
  `docs/experiments/三空间独立验证材料审计_20261025.md`。
- 不用随机初始化模型的白盒攻击直接与训练后模型比较（这正是 RQ2 需要两种扰动口径的原因）。
- 不因为结果不好看而删实验。失败、缺失、不适用都要留在表里。

## 8. 立刻可做的事（不依赖服务器、不依赖新算力）

1. ~~**RB40 的 bootstrap 置信区间**~~ **已完成（2026-11-12）**：`results/audits/bootstrap-rb40-20261112.md`。
   结论是 Φ 与 `adversarial_loss` 在 40 个已训练模型上稳定为正，R-Score/Ψ 的方向分辨不出来
   （区间跨 0），两套排序"不一致"但**不能**说"反向"。
   由此产生一条**数据需求**：要分辨 R-Score 的方向，需要更多已训练防御模型（或更多随机种子下的
   同一批模型），这不是分析能补的。已并入 M3 的数据计划。
2. ~~**Φ 增量检验**（M1）~~ **已完成（2026-11-12）**：`results/audits/phi-incremental-20261112.md`。
   Δρ = +0.695 [+0.583, +0.769]、p = 0.0005、嵌套 R² 增量 +0.476；两个稳健性对照 0.685 / 0.676。
   结论：Φ 不是漂移族的重复。**剩下的不是分析问题，是机制问题**——为什么它能补上那部分信息，
   需要新的实验设计（例如在受控合成数据上让"一致性"与"幅度"分离），不在本文档 M 系列里。
3. **分网格榜**（可选）：把 RB40 / NB201 / DARTS 三套名次各出一张表，作为八设置总榜的附录。
   有了 bootstrap 之后，这张表必须带区间，否则不比总榜更有信息量。
4. ~~**RQ2 试点的数据准备**：把 16 个架构的 e0 指标先全部算出来~~ **已改为更大的目标（2026-11-12）**：
   RobBench 有 6466 个架构的训练后结果，而已有 e0 指标的只有 64 个。第一步应该是**把 e0 指标
   扩到更多架构**（每个约 4 秒，数百个架构只需数小时 CPU），而不是先训练 16 个。
   这样能在不花训练算力的前提下，把 3.4 的偏相关估计从 n=64（区间 ±0.25）压到可判读的宽度。
